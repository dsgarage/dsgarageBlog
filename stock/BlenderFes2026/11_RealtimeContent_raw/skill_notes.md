## 前提・環境

- 【話者】題材は NEWoMan TAKANAWA の常設 LED。縦長 LED 2 面(IMAGINATION OCEAN / IMAGINATION GARDEN、約 1 分 30 秒のループ映像)と、別エリアの横長 LED(IMAGINATION GARDEN の体験型バージョン)
- 【話者】縦長 2 作品はアドオン不使用、Geometry Nodes で制作し、デザイン〜アニメーション〜コンポジット〜レンダリングまで Blender のみ
- 【話者】レンダラーは基本的に Cycles。解像度は 8K 超
- 【話者】担当区分: raw inc. = ビジュアルデザイン + Blender から実装側への受け渡しを含むシステム設計。実装は Enigma(表記要確認)が担当し、本番は TouchDesigner
- 【画面】Blender のバージョンは画面からは特定できない(要確認)

## 判断基準 1: 描画方法の 3 択

| 方法 | 長所 | 短所 | 例 |
|:---|:---|:---|:---|
| プリレンダリング | 高画質を作り込みやすい | 時間軸が固定 | Blender / Cinema 4D / Houdini |
| リアルタイムレンダリング | 自由度・反応性が高い | 処理負荷と画質の調整が必要 | Unity / Unreal Engine / TouchDesigner / openFrameworks |
| ハイブリッド | Blender の質感を保ったまま体験者に反応できる | 状態が増えるほど素材数・組み合わせが増える | ゲームのイベントムービー切り替え |

- 【画面】判断軸は「画質／実装工数／修正方法／チーム体制」
- 【話者】求められたのは「GI の効いた、密度のあるリッチなルック」。全部リアルタイムで描くとゲームっぽい見た目になる懸念があり、映像素材方式を採用
- 【話者】検討して見送った別案: (a) Alembic 等で 3D モデル+アニメーションを渡しリアルタイム側で描画、(b) Unity HDRP、(c) Unreal Engine のレイトレーシング。いずれもスタディ段階で想定ルックに届かなかった
- 【話者】映像素材方式はデザイナー(Blender で素材)とエンジニア(再生・体験制御)の責任範囲を切り分けやすい。別会社と組むときに効く
- Skill 化の判断ルール案: 「ルック最優先 + 実装チームが別 + 状態数が有限」ならハイブリッド(映像素材方式)。「その場で位置・大きさを変えたい + 状態数が多い」ならリアルタイム 3D を優先検討

## 手順: Blender → リアルタイム側への持ち込み(映像素材方式)

1. 体験者の動き・必要な状態・起こりうる破綻を洗い出す
2. 必要な映像素材、前後関係、影のパターンを設計する(素材数と作業量をここで割り出す)
3. Blender で制作し、書き出す
4. Unity で体験と再生状態を事前シミュレーション・デバッグする(自社でシミュレーター用アプリを開発)
5. TouchDesigner で本番実装する
6. 現場の実寸 LED で確認する
7. Blender に戻って修正 → 再出力 → 再確認。3〜7 を回す

- 【話者】最初に「この方式で映像を渡す」というテスト用サンプルデータを実装側に渡し、実装と素材制作を並行させ、最後に現場でマージした

## データ形式・素材の切り方

- 【話者】コーデックは HAP(アルファ付き)。花のグループごとに書き出す
- 【事実】HAP は GPU でデコードする動画コーデック群で、HAP Alpha / HAP Q Alpha がアルファチャンネルを持つ。TouchDesigner の Movie File In TOP で再生できる(変種の選択は要確認)
- 【話者】横長 LED の花は横方向に 8 グループ、さらに前後(奥行き)のレイヤーごとに別素材
- 【画面】アウトライナーは `flowers` コレクション配下に `a` / `b` / `c` / `d` ... のグループ、その下に `a_front` / `a_back` のように前後で分けたコレクション。各植物はカーブオブジェクト(名前は `10.007` のような番号)
- 【画面】縦長作品のシーンでは `[01]_main` / `[01]_flower` / `[01]_bubble` / `[01]_sky` のように作品番号を接頭辞にした命名。アセット側は `[Asset]_leafA.001` のような接頭辞
- 【話者】デザイナーとエンジニアで「素材仕様・命名・再生ルール」を共有することが必須

## 状態遷移の設計(時間軸が固定されない問題)

- 【話者】映像のタイムラインではなく「状態」と「状態遷移」として設計する
- 【画面】1 本の映像を 3 区間に分ける例: 600F 中、0〜50F 成長 / 51〜550F 咲いた状態で揺れるループ / 551〜600F しぼむ
- 【画面】入場: 成長区間を再生 → 滞留: 揺れ区間をループ(550F の後 51F に戻る) → 退場: ループを抜けてしぼむ区間へ
- 【話者】落とし穴: ループ序盤で人が離れると、しぼむ区間に達するまで待ちが生じる。退場時は再生速度を早回しにする、切り替えタイミングを調整するなど再生制御側で吸収
- 【話者】「技術的に正しいだけでなく、反応が気持ちよく感じられるか」を基準に調整する
- Skill 化メモ: ループ区間の始点・終点を映像内で見た目が連続するように作っておく(ループの継ぎ目)。講演では明言なし(要確認)

## 落とし穴と対処

- 【話者】配置・前後関係が固定され、「この位置 = この植物」の対応が体験者にバレてランダム感が消える → リアルタイム側で花びらを奥行き付きで舞わせる。手前に植物があれば奥に隠れるため、見え方が状況ごとに変わる
- 【話者】全グループ並んだ状態でレンダリングすると花同士の影が焼き込まれ、1 グループだけ表示したときに不自然 → 周囲の有無に応じた影あり/影なし素材パターンを用意し、状況で差し替える
- 【話者】状態が増えるほど素材の組み合わせが爆発する → 全組み合わせを作らず、破綻する条件を先に見つける。エリア・グループ・前後関係を管理できる単位に整理
- 【話者】PC 画面で良くても実寸 LED では動きが速すぎる、細部が見えない、影や重なりの粗が見える、反応速度の感じ方が違う → 現場確認を最初から工程に組み込む。現場調整は「最後の微調整」ではない
- 【話者】事前シミュレーションで「大きな課題と思ったものが気にならない」「別の問題が出る」ことが多い → 現場入り前に Unity 等で再生状態をシミュレーションする
- 【話者】映像素材方式の弱点: 修正のたびに Blender へ戻り再レンダリング → 素材を渡し直し。素材数が多いほど確認コストが増える(リアルタイム 3D ならその場でパラメータ調整できる)

## リアルタイム向けの最適化(レンダリング・運用)

- 【話者】8K 超でレンダリング時間が読めないため、レンダーサーバー + 社内/自宅のローカル PC で分散レンダリング。Blender は無料なので台数を増やしやすい
- 【話者】アドオン・プラグインのライセンス制約で制作環境を 1 か所に絞る必要が生じない点も Blender を選んだ理由
- 【事実】再生側の負荷対策として、グループ・レイヤーごとに素材を分けると必要な素材だけを再生できる。HAP は CPU デコード負荷が低い(一般論、講演では「処理的に HAP」とのみ言及)

## Geometry Nodes の組み方(修正に強い仕組み)

- 【話者】コンセプトは「変更し続けられる制作システム」。見た目だけでなく、実装に合わせて修正できる仕組みを作る
- 【話者】植物は茎・葉・花びらの基本構造に分け、構造と組み方は全種共通。花びらの枚数や葉の分岐まで仕組み化し、組み合わせと変数でバリエーションを出す
- 【話者】どのノードを組み合わせるとどんな植物になるか、という決め事を制作前にデザイナー間で共有 → 別の人が作っても同じパラメータで直せる
- 【話者】修正が入りそうな箇所(アニメーション速度、花びらの大きさ等)を最初からグループ入力としてモディファイアーに出しておく
- 【話者】終盤(現場検証フェーズ)はノードエディタを基本的に開かない。モディファイアーの値調整と参照オブジェクトの差し替えだけで修正する
- 【画面】カーブオブジェクトに GN モディファイアー `flower` と `plant` の 2 段。`plant` ノードグループは多数のオブジェクトで共有(ユーザー数 122 と表示)
- 【画面】`plant` モディファイアーに出していたパネルと入力名の例:
  - 最上位: `growth`(成長度)、`growth_noise`、`curveResample`
  - animation: `sway_strength`、`flower_scale_min` / `flower_scale_max`、`index_child_scale`、`index_child_tilt_min` / `_timing`、`index_leaf_tilt_min` / `_timing`
  - leaf_FX: `a_min`、`b_min`、`a_maxRange_min/max`、`b_maxRange_min/max`
  - color: `leaf`、`leaf_FX_Setting`、`vine`、`stem`、`child_color_index`
  - material: `leaf`、`leaf02`、`vine`、`stem`
  - object: `vine`、`leaf`、`leaf02`、`leaf03`(参照オブジェクト `[Asset]_leafA.001` 等)
  - setting: `vine` / `flower` / `leaf` / `extra_leaf` / `child` の表示切り替え
  - stem: `stem_rad_end`、`stem_rad_fac`、`stem_res`、`stem_end_mesh`
  - leaf: `leaf_original`、`extra_leaf`、`leaf_count`、`leaf_delete_upper/under`、`leaf_rotate`、`leaf_rotate_offset`、`leaf_slope`、`leaf_scale_end`、`leaf_scale_fac`
- 【事実】Geometry Nodes のグループ入力はモディファイアーパネルに表示され、パネル(折りたたみ)で分類できる。オブジェクト/マテリアル型の入力も公開でき、参照の差し替えがノードを開かずに行える
- Skill 化メモ: 入力名は snake_case、パネル名で「animation / color / material / object / setting / 部位名」に分ける構成がそのまま流用できる。`growth` のような 0〜1 の成長度を最上位に置き、アニメーションはこの 1 値にキーを打つ設計が読み取れる(キーの打ち方は講演で明言なし、要確認)

## 今後への期待(話者の意見)

- 【話者】Geometry Nodes のノード・アセットの再利用、管理、共有がさらにしやすくなってほしい(チーム制作向け)
- 【話者】表現に応じたレンダラーの選択肢と品質向上。Cycles だと「Cycles っぽく」なる
- 【話者】AI: プログラミングは「設計 → AI で実装 → デバッグ」が実用段階。3DCG はまだ意図どおりに制御しにくい。全生成より、簡単なモデリング、Geometry Nodes の下地作成、ノードの整理・アセット化・最適化・命名管理など途中作業の支援に期待

## まとめ(Skill の冒頭に置く原則)

1. 体験から逆算する: 最終的な空間と人の動きから、必要な表現と仕組みを決める
2. ツールの役割を分けてつなぐ: Blender で絵を作り、リアルタイムツールで体験を動かす
3. 作る → 試す → 直す、を回せるようにする: Geometry Nodes を量産だけでなく修正・検証に使う
